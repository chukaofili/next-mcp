## Prompt 1 — Start the recommended fixes

For a fresh Claude Code session that will execute follow-ups using
subagent-driven development. The recommended-fixes doc has 7 tiers;
this prompt scopes to Tier 2 first and gates further tiers on user
review.

```text
Read docs/plans/2026-05-06-recommended-fixes.md.

Skip Tier 1 (those are gated on the smoke run). Pick up Tier 2 first
using superpowers:subagent-driven-development:

  - Tier 2a: audit `generate_base_components` for monorepo path
    correctness, fix any bare-`projectPath` uses, add monorepo tests
    (~3 tests). Spec + code review combined since it's small.
  - Tier 2b: add a test asserting `setup_shadcn` × full × shadcn
    fires both `shadcn init` invocations (apps/web AND packages/ui)
    with correct cwds, using the NEXT_MCP_RECORD_COMMANDS env-var
    pattern from G2. ~1 test.
  - Tier 2c: audit `turbo.json` template content; add a test
    asserting it has the right `tasks` entries for build/lint/
    typecheck/test.

Stop after Tier 2 is complete and check in with me before starting
Tier 3 (cross-field schema refines) — I want one tier at a time so I
can review the diff between each.

Branch is `feat/upgrade-packages`. HEAD is `693eb76`. Tests baseline
is 14 files / 185 tests. The handoff doc at
docs/plans/2026-05-05-monorepo-support-handoff.md is ARCHIVED — read
it only for the per-group "in-context nuances" sections if you need
to understand a prior decision; don't update it.
```

### When to use this prompt
- After pushing the current branch state (`git push origin
  feat/upgrade-packages`) so the new session sees the same code.
- In a fresh Claude Code session in this repo (so the system prompt
  picks up the right working directory and git state).

### Notes for adapting the prompt
- To work on a different tier, replace the Tier 2 bullets with the
  target tier's items from `2026-05-06-recommended-fixes.md`. Keep
  the "Stop and check in" instruction unless you want continuous
  execution across tiers.
- Tier 1 items require the smoke run output (Prompt 2 below) to be
  available — don't dispatch Tier 1 from a code-only session.
- Tier 4 (helper extractions) and Tier 6 (deferred minors) are
  good "polish pass" candidates if you want to bundle small wins
  into one session.

## Prompt 2 — Smoke-test coworker

For an interactive session (Claude Code in a separate terminal, or
Claude.ai chat) where **you** run the actual shell commands and
Claude helps interpret output and capture findings. This is the
manual smoke run promised in `docs/plans/2026-05-05-monorepo-smoke-test.md`.

```text
You are helping me run a manual end-to-end smoke test of the
monorepo support work in next-mcp. The procedure is documented at
docs/plans/2026-05-05-monorepo-smoke-test.md — read it first as the
source of truth.

Working dir: /Users/chukaofili/projects/chukaofili/next-mcp
Branch: feat/upgrade-packages
HEAD: 693eb76 (or current — `git log --oneline -1` to verify)
Test baseline: 14 files / 185 tests passing
Smoke variants: everything-on full + variants A (npm), B (bun+
sqlite+drizzle), C (minimal), D (flat regression).

Your role:
  1. I drive — I run the commands locally (MCP inspector calls,
     pnpm install, docker build, docker compose run, etc.). I will
     paste the output back to you.
  2. You interpret — for each tool result and each shell command
     output, compare it against the smoke doc's per-tool checklist
     (section 4) and build steps (section 5). Tell me explicitly
     which assertions pass and which fail.
  3. You capture findings — when something fails or is surprising,
     draft the entry for the doc's "Findings" section (section 8).
     Keep it tight: date, observation, error verbatim, suggested
     follow-up ticket title.
  4. You do NOT run shell commands or edit files. This is your
     read-only / advisory mode. The only file you may write to is
     `docs/plans/2026-05-05-monorepo-smoke-test.md`'s Findings
     section, and only when I confirm.

Start by:
  - Confirming you've read the smoke doc.
  - Asking which variant I want to run first (recommend
    "everything-on full" — it's the reference).
  - Listing the steps I should run for that variant from sections
    3-5, and what output you need from me at each step.

Known carry-over context (from
`docs/plans/2026-05-06-recommended-fixes.md` Tier 1):
  - Group K just shipped Dockerfile.migrate templating; the
    `docker compose run --rm migrate` step is its first runtime
    test. Watch for it.
  - The better-auth CLI cwds (`packages/auth` for schema-gen,
    `packages/db` for migrations) are also first-runtime here.
  - shadcn `--preset b0 --template next --monorepo --pointer` is
    a newish format; flag any registry/CLI hiccups.

If something looks like it's actually a bug (not a smoke-procedure
gap), say so explicitly with file:line references and propose
either a fix-now or a follow-up ticket. Don't try to fix it
yourself — I'll handle the implementation in a separate session.
```

### When to use this prompt
- When you have a Docker daemon running, ~30 minutes of focus, and
  network access to npm + GitHub + better-auth-ui.com.
- The smoke is the gating step before merging
  `feat/upgrade-packages` to `main`. Run it first.

### Notes for adapting the prompt
- For a single-variant smoke (e.g., just the everything-on full
  smoke), drop the variant list and tell the assistant directly
  which one you're running.
- If you want the assistant to be more autonomous (e.g., update the
  Findings section without confirmation), relax rule 4. Default is
  conservative because the doc is the source of truth for the
  merge decision.
- If a finding turns into "this is actually a bug", switch sessions
  to one with Prompt 1 active (or a fresh implementer-style
  session) — the smoke session is read-only by design.

## After both prompts have run

When Tier 2 is done AND the smoke is green:

1. Update `docs/plans/2026-05-06-recommended-fixes.md`:
   - Mark Tier 2 items as ✅ done with commit SHAs.
   - Move any smoke-discovered bugs from Tier 1 into a new
     "Smoke findings" section or link to filed issues.
2. Decide on Tier 3 (schema refines) — small, ergonomic win,
   suitable for a polish session.
3. Open the merge PR for `feat/upgrade-packages` → `main`. Pull
   from the smoke doc's "Findings" section as part of the PR
   description so reviewers see what was verified.
