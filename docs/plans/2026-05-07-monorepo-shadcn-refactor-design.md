## 1. Summary

When `uiLibrary === 'shadcn'` and `monorepo !== 'none'`, replace the
current `create-next-app + scaffoldMonorepoRoot + generateFullModePackages`
pipeline with a single delegation to `shadcn@latest init --monorepo`. The
shadcn CLI, in CLI v4 (March 2026), scaffolds the entire workspace
skeleton in one shot — root files, `apps/web/`, `packages/ui/`,
`packages/eslint-config/`, `packages/typescript-config/`, `turbo.json`,
`pnpm-workspace.yaml`, and a properly cross-aliased `components.json`
in both apps/web and packages/ui — with no `create-next-app` involvement
and therefore no rogue `apps/web/pnpm-workspace.yaml` shadowing.

next-mcp then **augments** the shadcn scaffold with the things shadcn
doesn't do: project-scoped package rename (`@workspace/*` →
`@<projectName>/*`), database/auth/orpc packages, Docker layer, testing
setup, `.env*` files, catalog block, and version-pin alignment.

Outside the shadcn paths (`uiLibrary !== 'shadcn'`), the existing
manual scaffolding stays — but with the targeted B5 fix (delete
create-next-app's leftover `apps/web/pnpm-workspace.yaml` and
`apps/web/pnpm-lock.yaml`) so those paths also stop tripping over the
same workspace-shadowing bug.

This refactor is high-leverage: it eliminates the entire B1/B2/B3/B5
failure cluster surfaced in the smoke, cuts ~hundreds of lines of
template-emission code, and gets the cross-workspace `globals.css`
link that's the actual point of monorepo+shadcn (which the current
implementation does not achieve).

## 2. Background — what the smoke surfaced

The 2026-05-07 smoke run on `feat/upgrade-packages` exercised the
"everything-on full" variant (`pnpm + postgres + prisma + better-auth +
shadcn + orpc`, monorepo: full). Five tool calls were attempted via the
MCP inspector. Headline outcomes:

| Tool | Outcome |
|---|---|
| `scaffold_project` | Returned success (CLI subprocess clean), but silently emitted broken workspace state — see B5. |
| `setup_database` | Returned success. Prisma client generated. |
| `setup_authentication` | Returned **success-with-warning** ("⚠️ Manual setup required"). Two silent subprocess failures hidden behind that wrapper — see B1, B3. |
| `setup_shadcn` | Returned `isError: true` — first hard MCP error. See B2. |
| `generate_dockerfile` / `generate_readme` / `validate_project` | Not run — smoke paused once the architectural pattern was clear. |

The seven findings filed against the smoke (full text in the smoke doc's
Findings section, "Everything-on full" subsection):

- **B1** — `setup_authentication`'s better-auth schema-gen silently fails
  on the prisma path (`dotenv-cli` not wired; subprocess fails;
  `execCommand` swallows it; tool falls through to a "Manual setup
  required" branch with no `isError`).
- **B2** — `setup_shadcn` invocation incompatible with shadcn CLI v4's
  `--monorepo` semantic. `buildShadcnInitCommand` (`src/index.ts:533-540`)
  hardcodes `--monorepo`, but in CLI v4 that flag is for
  *scaffold-from-scratch*, not "configure existing monorepo". Docs
  contradict the assumption: <https://ui.shadcn.com/docs/monorepo>.
- **B3** — `setup_authentication`'s better-auth-ui shadcn registry pulls
  silently no-op. `execCommand` reports success on registry calls that
  produced zero output files because the workspace was in the broken
  state from B5.
- **B4** — Tool-pipeline architectural gap: no `<pm> install` between
  `scaffold_project` and downstream `setup_*` tools. Subprocess flow
  assumes a hydrated workspace that no one has actually populated.
- **B5 ⭐** — `create-next-app --use-pnpm` emits
  `apps/web/pnpm-workspace.yaml` (just `ignoredBuiltDependencies`) and
  `apps/web/pnpm-lock.yaml`. `scaffoldProject` does not delete these
  after the subprocess returns. Effect: every later `pnpm <add|install>`
  invoked from inside `apps/web/` walks up, finds
  `apps/web/pnpm-workspace.yaml` first, treats `apps/web/` as the
  workspace root, fails to resolve workspace deps with
  `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`. **Root cause behind B1, B3, and
  the `pnpm add` half of B2.** Reproduced and confirmed: deleting both
  files made `pnpm m ls` from apps/web correctly enumerate all 8
  workspace projects.
- **B6** — `execCommand` swallows silent failures across multiple tools
  (success criterion is exit-code-only, not output-verification).
- **B7** — Doc drift: smoke doc section 4 line 192-194 schema-gen cwd
  assertion (`packages/auth`) is stale; `getAuthSchemaCwd` returns
  `projectPath`.

## 3. Goals & Non-Goals

### Goals

1. **Eliminate B5 by construction** — no `create-next-app --use-pnpm`
   in the monorepo+shadcn paths means no rogue `apps/web/pnpm-workspace.yaml`
   ever exists.
2. **Eliminate B2 by construction** — shadcn's CLI is the one in charge
   of its own monorepo invocation contract; next-mcp stops tracking
   shadcn's flag-semantic changes across CLI versions.
3. **Reduce code surface area.** Roughly all of `scaffoldMonorepoRoot`
   (`src/index.ts:1496-1606`) and the manual emission of
   `packages/eslint-config/`, `packages/typescript-config/`, and
   `packages/ui/` from `src/templates/packages/*` becomes redundant.
   Several dozen template files can be deleted.
4. **Achieve cross-workspace design-system sharing.** shadcn's monorepo
   scaffold writes `apps/web/components.json`'s `tailwind.css` to
   `../../packages/ui/src/styles/globals.css` — a single source of truth
   for design tokens. next-mcp's current emission gives apps/web its
   own globals.css, defeating the point of putting shadcn in a monorepo.
5. **Apply the targeted B5 fix to non-shadcn paths too.** Even where R1
   doesn't apply (`uiLibrary !== 'shadcn'`), the rogue file deletion
   needs to happen for the same reason.
6. **Defense-in-depth via B6 fix.** Strengthen `execCommand`'s success
   criterion so silent failures in any tool (not just the ones surfaced
   here) raise `isError: true` going forward.

### Non-Goals

- **Refactoring the non-shadcn flat-mode (`monorepo: 'none'`) path.** It
  works today; B5's targeted fix is enough for it.
- **Refactoring `setup_database`, `setup_authentication`, `setup_shadcn`'s
  business logic** beyond what this scaffolding change requires. Auth's
  CLI-invocation paths (B1) get a focused fix in their own ticket.
- **Adding new architectural choices** (e.g. supporting non-Turborepo
  monorepos, alternative bundlers). Stay within the `pnpm + turbo +
  Next.js` shape shadcn's CLI provides.
- **Moving to flat `apps/web/app/` layout** vs the current `apps/web/src/app/`
  is a contained sub-decision, not a goal of the refactor — see Open
  Questions.

## 4. Current architecture (what's there today)

### 4.1 The scaffolding entry point

`scaffoldProject` (`src/index.ts:1386-1460`) does:

1. Build a `create-next-app` command: `pnpm dlx create-next-app@^16
   ./web --ts --use-pnpm --src-dir --yes` (in monorepo mode) or analogous
   in flat mode.
2. Run it from `<projectPath>/apps/` (monorepo) or `<targetPath>` (flat).
3. In monorepo mode: `renameAppPackage` (renames apps/web's package.json
   `name` to `@<projectName>/web`), `ensureEnvExample`,
   `scaffoldMonorepoRoot`, `generateFullModePackages`.
4. Always (per-app): `updateGitignore`, `createDirectoryStructure`,
   `updatePackageJson`, `generateNextJSCustomCode`.
5. Optionally: `installDependencies` (when `!skipInstall`).

### 4.2 `scaffoldMonorepoRoot` (`src/index.ts:1496-1606`)

Emits these workspace-root files from templates in `src/templates/`:

- `package.json` (turbo + typescript devDeps; conditionally `dotenv-cli`
  for drizzle path; conditionally docker scripts; conditionally test
  script pruning when `testing === 'none'`)
- `tsconfig.json`
- `turbo.json` (with config-driven `globalPassThroughEnv`, optional task
  pruning when `testing === 'none'`)
- `.gitignore`
- `pnpm-workspace.yaml` (only for pnpm; with the catalog block)
- `.env.example`

### 4.3 `generateFullModePackages` (`src/index.ts:1713+`)

For `monorepo: 'full'`, copies entire template trees from
`src/templates/packages/` into `<projectPath>/packages/`:

- **Always-on:** `eslint-config/` (with `base.js`, `next.js`,
  `react-internal.js`, `package.json`), `typescript-config/` (with
  `base.json`, `nextjs.json`, `react-library.json`, `package.json`).
- **Gated:** `db/` (per-ORM template tree under
  `packages/db/{prisma,drizzle,mongoose}/`), `auth/`, `ui/`, `orpc/`.
- The `db` package has additional dep patching via
  `patchDbWorkspacePackageJson`.

### 4.4 The templates that exist today

`src/templates/` (72 template files total):

## 6. Proposed architecture

### 6.1 Dispatch

```ts
async scaffoldProject(config, targetPath) {
  const projectPath = path.join(targetPath, config.name!);

  if (config.architecture.uiLibrary === 'shadcn'
      && config.architecture.monorepo !== 'none') {
    await this.scaffoldViaShadcnMonorepo(config, projectPath);
  } else if (config.architecture.uiLibrary === 'shadcn'
      && config.architecture.monorepo === 'none') {
    await this.scaffoldViaShadcnFlat(config, projectPath);
  } else {
    // existing path: create-next-app + scaffoldMonorepoRoot + ...
    // (with the B5 fix applied — see §6.4)
    await this.scaffoldViaCreateNextApp(config, projectPath);
  }

  // Common post-scaffold work (independent of shadcn vs create-next-app):
  await this.augmentScaffold(config, projectPath);
}
```

### 6.2 `scaffoldViaShadcnMonorepo(config, projectPath)`

```sh
pnpm dlx shadcn@latest init --preset b0 --template next --monorepo \
  --pointer --name <projectName> --cwd <projectPath>
```

(Or with `--silent` for less output noise; or with `--force` if we want
to be explicit about non-interactive overwrite.)

After it returns, run **augmentation passes** (in this order):

1. **Project-scoped rename.** `@workspace/*` → `@<projectName>/*` across:
   - all `package.json` `name` fields
   - all `package.json` `dependencies` and `devDependencies` workspace
     specifiers
   - all `tsconfig.json` `extends` and `paths`
   - all `components.json` `aliases`
   - any other config file referencing `@workspace/...` (eslint
     configs, etc.)

   Implementation: a recursive walker that reads JSON files (and a
   couple of JS/TS configs), does string-level replace on
   `"@workspace/` → `"@<projectName>/`. Should be a clean sweep.

   > **Phase 0 spike correction (2026-05-07):** the substring rewrite
   > is necessary but not sufficient — `apps/web/package.json.name`
   > is just `"web"` (unscoped, no `@workspace/` substring), so the
   > rewrite skips it. The rename pass must also do an explicit
   > `apps/web/package.json.name = "@<projectName>/web"` edit.
   > See [`2026-05-07-r1-spike-results.md`](./2026-05-07-r1-spike-results.md) §8.1.

2. **Insert pnpm-workspace catalog block.** Append the catalog: under
   `packages:`. Reuse the existing `CATALOG_VERSIONS` constants and
   `substituteCatalog` helper for the per-package substitution path.

3. **Pin alignment.** Decide pinning policy (see Open Questions §8.3),
   then update root `package.json`'s `packageManager`, `engines.node`,
   `engines.pnpm`, and the catalog `typescript`/`eslint`/`@types/node`
   versions. Decide whether to bump apps/web's next/react pins to match
   our existing baselines.

4. **Layout decision: keep flat `apps/web/app/...` or move to `src/`.**
   See Open Questions §8.2. If we keep flat, all next-mcp templates
   that emit into `apps/web/src/...` need their paths updated.

5. **Emit `.env`, `.env.example`, `.env.local` at workspace root.**
   Reuse `ensureEnvExample` (`src/index.ts:1486-1494`).

6. **Add docker scripts to root `package.json`.** Reuse the existing
   block from `scaffoldMonorepoRoot` lines 1543-1549.

7. **Conditional `dotenv-cli` devDep + `auth:generate` script** (when
   `getAuthGenerateScript(config)` is non-null — drizzle path). Reuse
   the existing block from `scaffoldMonorepoRoot` lines 1524-1534.
   Important: also wire `dotenv-cli` for the prisma path per ticket B1.

8. **Conditionally drop test scripts** when `testing === 'none'` (lines
   1558-1566 + 1584-1587 of current scaffoldMonorepoRoot logic).

9. **Conditionally emit downstream packages.** Call into the existing
   gated emitters for db / auth / orpc — `copyPackageTemplate` against
   `templates/packages/{db,auth,orpc}/` (those templates stay).

10. **`patchDbWorkspacePackageJson`** for the prisma/drizzle/mongoose
    runtime/dev deps the templates don't enumerate.

11. **`updateGitignore` + `createDirectoryStructure` + `updatePackageJson`
    + `generateNextJSCustomCode`** for apps/web — same as today.

### 6.3 `scaffoldViaShadcnFlat(config, projectPath)`

```sh
pnpm dlx shadcn@latest init --preset b0 --template next --no-monorepo \
  --pointer --name <projectName> --cwd <projectPath>
```

Augmentations: subset of the above — no rename pass needed (single
package), no catalog/turbo concerns, but still need `.env*`, docker
scripts in apps's `package.json`, db/auth setup paths, etc. Effectively
the same as today's `scaffoldFlat` minus `create-next-app`.

### 6.4 Non-shadcn fallback (existing path with B5 fix)

For `uiLibrary !== 'shadcn'`, keep the existing
`buildCreateNextAppCommand` + `scaffoldMonorepoRoot` +
`generateFullModePackages` flow. Add a one-liner after `create-next-app`
returns:

```ts
// In monorepo modes, create-next-app --use-pnpm leaves
// apps/web/pnpm-workspace.yaml (just ignoredBuiltDependencies) and
// apps/web/pnpm-lock.yaml. They shadow the real workspace one level
// up, breaking every subsequent `pnpm <add|install>` from inside
// apps/web. Delete them before any downstream tool runs.
if (isMonorepo) {
  await fs.rm(path.join(appPath, 'pnpm-workspace.yaml'), { force: true });
  await fs.rm(path.join(appPath, 'pnpm-lock.yaml'), { force: true });
}
```

This single edit closes B5 for the non-shadcn paths (and is also a
useful *belt-and-suspenders* even for the shadcn paths if `--use-pnpm`
ever creeps back in).

### 6.5 `<pm> install` between scaffold and downstream tools (B4)

Independent of R1. Two options:

- **(a)** Add an explicit install step at the end of `scaffoldProject`
  (already partially in place at `src/index.ts:1435-1438` — the
  `if (!skipInstall)` branch). Make this run for monorepo modes too,
  not just flat — verify it currently does.
- **(b)** Add a guard at the top of each downstream `setup_*` tool
  that runs `<pm> install` if `<projectPath>/node_modules/` doesn't
  look hydrated. Slightly more defensive but slower if it runs
  redundantly.

Recommend (a) for simplicity; (b) only if (a) misses an edge case.

### 6.6 `execCommand` strict success criterion (B6)

Independent of R1. Change the success contract to be "exit code 0 AND
expected outputs exist". Implementation sketch: each
`this.execCommand(...)` call site that has known-output expectations
(file paths, directory contents) gets a third callback that verifies
the outputs and downgrades to `success: false` if missing. Or: wrap
`execCommand` in a higher-order helper `execAndVerify(cmd, cwd, label,
verifyFn)`. Surfaces stderr in the MCP response when `success: false`.

This is a defense-in-depth concern across all setup tools; not blocking
R1.

## 8. Open questions / decisions needed

### 8.1 What does `--name` actually rename?

Docs say "the name for the new project" (terse). Need to empirically
verify against `pnpm dlx shadcn@latest init --name foo --cwd /tmp`:

- Does it rename the *directory* (e.g. `/tmp/foo`)?
- Does it set root `package.json` `name`?
- Does it change the `@workspace/...` scope to `@foo/...`? (Bet: no —
  scope appears hardcoded; if it does change, the rename pass in §6.2
  step 1 becomes unnecessary.)

If `--name` *does* rename the scope, half the augmentation work
disappears. Worth ten minutes of empirical testing before settling on
the rename pass shape.

### 8.2 `apps/web/src/` vs flat `apps/web/app/`

Today next-mcp's templates assume `apps/web/src/app/...` (next-mcp's
`buildCreateNextAppCommand` uses `--src-dir`). shadcn's monorepo init
produces flat `apps/web/app/...`.

**Option (a):** keep next-mcp's `src/` convention. After shadcn init,
move `apps/web/{app,components,hooks,lib}` under `apps/web/src/` and
update `apps/web/tsconfig.json` `paths` (`@/*` from `["./*"]` to
`["./src/*"]`) and `apps/web/components.json` `tailwind.css` (relative
path adjusts up one level).

- **Pro:** zero churn to `setup_database` / `setup_authentication` /
  `setup_shadcn` / `generate_*` templates that emit into
  `apps/web/src/...`.
- **Con:** post-scaffold gymnastics; future shadcn CLI updates that
  change the flat layout could break the move pass.

**Option (b):** adopt shadcn's flat convention. Sweep all next-mcp
templates and code references from `apps/web/src/...` to `apps/web/...`.

- **Pro:** structurally cleaner; matches what shadcn (and Turborepo
  starter convention) does.
- **Con:** larger diff; touches every template under `src/templates/`
  and every path resolver in `src/index.ts` (e.g. `getAppPath`,
  `getAuthFilePaths`, etc.).

**Recommendation:** (b) if R1 is being done anyway — the diff is bigger
but cleaner and the result is more idiomatic. Tracker for *which*
files/templates need the sweep should be generated as part of Phase 0.

> **Phase 4 landed: option (a)**, overriding the spike-results
> recommendation of (b). Reason: blast radius. Option (a) is a single
> mechanical post-init move (`apps/web/{app,components,hooks,lib}` →
> `apps/web/src/...`) that leaves every existing path resolver and
> emit-into-`src/` template untouched. Option (b) would have required
> touching `getAppPath`, `getAuthFilePaths`, `generateNextJSCustomCode`,
> and the privacy/terms templates in lockstep. The move pass is
> implemented as `moveAppsWebFlatToSrc` in `src/index.ts` (idempotent;
> patches `apps/web/tsconfig.json` `paths` and
> `apps/web/components.json` `tailwind.css` accordingly).

### 8.3 Version-pin policy

shadcn's monorepo scaffold pins:

- `pnpm@9.15.9` (vs next-mcp's `pnpm@10.18.0`)
- `next@16.1.6` (vs next-mcp's `^16.2.x`)
- `node>=20` (vs next-mcp's `>=24`)
- `typescript@5.9.3` (vs next-mcp's `CATALOG_VERSIONS.typescript` =
  `^6` — **does not match**, override required; corrected from the
  Phase 0 spike, see [`2026-05-07-r1-spike-results.md`](./2026-05-07-r1-spike-results.md) §8.3)
- `react@^19.2.4` (matches)

**Option (a):** accept shadcn's pins as the new baseline. Simpler
implementation. Side effect: existing users would experience a
*downgrade* of pnpm, next, node minimums. Maybe acceptable, maybe not
— depends on what we've already shipped to users.

**Option (b):** post-scaffold pin-bump pass. Update root `package.json`
`packageManager`, `engines`, and per-package `dependencies` to next-mcp's
existing pins. Implementation cost: small (a few JSON edits).

**Recommendation:** (b). The pnpm 10.0.0 workspace regression note in
the current source (`src/index.ts:1517-1519`) is non-trivial domain
knowledge — preserving the `pnpm@10.18.0` pin matters.

### 8.4 What does `monorepo: 'minimal'` mean post-R1?

Today, "minimal" is "scaffold apps/web only — no packages/*". shadcn's
`--monorepo` flag scaffolds the full skeleton (apps/web + packages/ui +
packages/eslint-config + packages/typescript-config) — no minimal mode.

**Option (a):** treat "minimal" as "full skeleton, but db/auth/orpc
stay out" — i.e. always have packages/ui + packages/eslint-config +
packages/typescript-config, but skip the per-feature packages.

- **Pro:** matches the ergonomics of shared design system + shared
  configs even for "minimal" projects. The shadcn CLI naturally produces
  this.
- **Con:** behavioral change. Existing "minimal" users would see new
  packages/* directories appear.

**Option (b):** for minimal, fall back to `--no-monorepo` (flat) and
re-introduce a manual "single-app-with-packages" emission. More work,
preserves backward compat.

**Option (c):** drop the "minimal" mode entirely. Unify on
`monorepo: 'full' | 'none'`. Worth considering if (a) means minimal
isn't really minimal anymore.

**Recommendation:** (a) initially, with a changelog note. If user
feedback flags the behavioral change, revisit.

> **Phase 4 landed: option (a)** as recommended. `monorepo: 'minimal' +
> uiLibrary: 'shadcn'` produces shadcn's full skeleton (apps/web +
> packages/ui + packages/eslint-config + packages/typescript-config)
> with no per-feature db/auth/orpc packages. The smoke v2 doc's Variant
> C tests `monorepo: 'minimal' + uiLibrary: 'none'`, which keeps Path B
> semantics (apps/web only, no packages/) — that's still validated by
> the existing smoke variant.

### 8.5 How do we guard against shadcn CLI breaking changes?

R1 puts shadcn's CLI on the critical path. shadcn already changed
`--monorepo`'s semantic between v3 and v4 (the inciting incident for
this refactor).

**Mitigation candidates:**

- Pin shadcn version explicitly in our `init` invocation:
  `shadcn@^4.7.0` (matching `/tmp/test-2`'s `packages/ui` dep) instead
  of `shadcn@latest`. Trade-off: misses CLI improvements.
- Add a CI check that periodically runs `shadcn init --monorepo`
  against a throwaway dir and asserts the output structure matches our
  augmentation expectations. Surfaces regressions as smoke alerts
  rather than user incidents.
- Run the shadcn init via `pnpm dlx <pinned-version>` and only bump
  intentionally.

**Recommendation:** pin to `shadcn@<known-good>`, plus the periodic CI
check. Bump deliberately.

> **Phase 4 landed: deferred.** scaffoldViaShadcnMonorepo /
> scaffoldViaShadcnFlat invoke `pnpm dlx shadcn@latest init …`
> (unpinned) for now. Pinning is mechanically a one-line change
> (`shadcn@latest` → `shadcn@<version>`); deferred so the smoke matrix
> can drift its expectations alongside shadcn's evolving b0 preset
> without a tight version coupling. Track via a periodic CI smoke run
> that catches regressions. Revisit if shadcn ships a breaking change
> that affects the augmentation pipeline.

### 8.6 What about npm / yarn / bun for the package manager?

shadcn's CLI invocation `pnpm dlx shadcn@latest init` is package-manager-
agnostic for the *invocation* (we can use `npx`/`yarn dlx`/`bunx --bun`
for the same). But what shadcn *generates* may pin pnpm in the root
`package.json`'s `packageManager`. Verify against `/tmp/test-2`:
yes, `packageManager: pnpm@9.15.9` is hardcoded.

**For non-pnpm package managers**, the augmentation pass needs to:
- Override `packageManager` field
- Add `workspaces: ['apps/*', 'packages/*']` to root `package.json`
  (npm/yarn classic workspace declaration)
- Skip writing `pnpm-workspace.yaml` (or delete what shadcn wrote and
  use root `package.json`'s `workspaces`)
- Run package-manager-specific install (`npm install`, `yarn install`,
  `bun install`) at augmentation end

This isn't blocking — it's just one more axis of the augmentation pass.

- **No breaking change for end users running `next-mcp` against fresh
  scaffolds.** Output filesystem shape changes (e.g. apps/web layout,
  packages/ui contents), but the public MCP tool surface stays the same.

  calls. Users with existing projects see no change.
- **Integration tests will break and need updating in lockstep.** The
  test surface changes are tracked in Phase 5; unblock R1 by landing
  Phase 5 in the same PR, not lazily.

  `2026-05-05-monorepo-smoke-test.md` should be left as-is for the
  audit trail; smoke-v2 (Phase 6) is a fresh procedure against the new

  ever need to support older shadcn CLIs, the dispatch (§6.1) can fall
  back to the existing path — the existing path remains in the codebase
  during R1.
